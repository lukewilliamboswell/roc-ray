[#coming-from-raylib]
= Coming from raylib

RocRay draws, plays sound, and reads input through
https://www.raylib.com/[raylib], so much of it will feel familiar if you have
used raylib from C or another language. This chapter maps raylib's common
calls to their RocRay equivalents, and says what RocRay does differently. It
assumes <<app-model>>.

== What is different

The shape of a raylib program is a loop you write. In RocRay the host runs
the loop, and you supply `init!`, `update!`, and `render!`; <<app-model>>
explains why. Three differences matter most:

* *Each call has a place.* Drawing happens in `render!`. Anything that reads
  a file or otherwise waits happens in `init!` or a task. Everything else
  happens in `update!`. The _Where_ column below says which.
* *Input is a value.* `update!` receives this cycle's keys, mouse, time, and
  window state as `input`, rather than calling `IsKeyPressed` on global state.
* *Resources clean up after themselves.* Textures, sounds, fonts, and shaders
  are released when your model stops referring to them. There is no `Unload*`
  to call.

RocRay draws in 2D today. 3D models, cameras, and lighting are planned but not
yet available, so there is no `DrawModel`, `Camera3D`, meshes, or other 3D
drawing yet. There are no raw OpenGL (`rlgl`) calls, and there is no
file-open dialog: an app reads files the user drops on its window or names on
the command line, or directories it declares (see <<files-and-assets>>).

Rows marked `update!` are also legal in tasks, and most are legal in `init!`.
Each function's entry in the {api}[API reference] lists exactly where it may
be called.

== Collision is in Math, not Physics

RocRay has a `Physics` module, but it is not a physics engine. It implements
3D projective geometric algebra: points, lines, and planes in 3D, and the
_motors_ that rotate and move them. It is a mathematical toolkit for
specialised geometry.

For a 2D game, rectangles, circles, overlap tests, and vector arithmetic are
in `Math`, and gravity, velocity, and collision response are ordinary code in
your `update!`. <<input-time>> shows how to move things by elapsed time, with
a fixed step for stable physics.

== Performance expectations

Roc has no garbage collector. Memory is managed by _reference counting_: a
value is freed the moment nothing refers to it, so there are no collection
pauses in the middle of a level. When a value has only one reference, as
your model does while `update!` runs, Roc changes it in place instead of
copying it, so updating a large list of entities every cycle does not copy the
list.

How you run the app matters a lot:

* `roc main.roc` compiles quickly and runs the app at once. The code it makes
  is unoptimised: good for trying changes, not for judging speed.
* `roc build main.roc` makes an optimised executable (its default is
  `+--opt=speed+`). Build this way before you measure anything, and for
  release.

As a rough guide, on a desktop Linux machine the
{src}/examples/particles/main.roc[Particles] example (4,000 sprites, each
moved every cycle and drawn in one batch) spends about 0.07 ms per cycle in
`update!` when built with `roc build`, against about 0.5 ms under
`roc main.roc`. Drawing all 4,000 sprites takes about 0.3 to 0.4 ms of each
frame. Your numbers will differ, but that is the scale: a 60 frames per second
game has 16.7 ms per frame.

Two things commonly make a RocRay game slow:

* *Many separate draw calls.* Each `frame.texture!` call is a separate call
  from Roc into the host. For hundreds or thousands of sprites of one texture, build a list
  and draw it with one `frame.texture_instances!` call (see <<drawing>>).
* *Allocating every cycle.* Building new lists or strings every cycle is
  cheap in small amounts but adds up. Prepare text once with `Text.prepare!`,
  and keep lists in the model to update rather than rebuilding them.

To find out rather than guess, record a run with <<observatory>>, or set the
environment variable `ROC_RAY_ALLOC_STATS=1` to print how much each cycle
allocated (see <<reference>>).
