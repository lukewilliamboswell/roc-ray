[#examples]
= Example gallery

The repository's `examples/` directory holds complete apps and focused
recipes. Choose the one closest to what you want to build and copy its
directory. For the released examples, download the starter zip described in
<<getting-started>>; the checked-in examples on `main` may use APIs that have
not been released yet (see <<development-checkout>>).

Build from the directory that contains `examples/`, so asset paths resolve
consistently:

[source,sh]
----
roc build examples/snake/main.roc --output snake
./snake
----

== Start here

. Start with {src}/examples/hello_world/main.roc[Hello World] to see the
  complete app loop without asset loading or game rules.
. Change {src}/examples/pong/main.roc[Pong] to learn time-based movement,
  collision, input, scoring, and generated sound in one approachable file.
. Read {src}/examples/task_sleep/main.roc[Task Sleep] before adding files,
  networking, or any other work that waits.
. Pick a direction: {src}/examples/generated_assets/main.roc[Pixel Workshop]
  for an interactive tool, {src}/examples/responsive_ui/main.roc[Responsive
  Settings] for an app interface, or {src}/examples/snake/main.roc[Snake] for a
  state-driven game.
. Reach for a focused recipe only when your app needs that feature.

== Work that waits

Use these when copying the `Task.spawn!(input, || ...)` pattern described in
<<tasks>>. A task's return value arrives as one `Msg` on a later
`input.messages`.

[cols="1,3",options="header"]
|===
|Example |What it is
|{src}/examples/task_sleep/main.roc[Task Sleep] |One task, one `Task.sleep!`, one message back -- the shape of every other task on this page -- and printing done straight from `update!`, because a stream write queues rather than waits
|{src}/examples/async_read/main.roc[Async Read] |Two file reads and a `metadata!` call in flight at once, each with its own `Msg` variant, so none of them needs an id
|{src}/examples/capture_screenshot/main.roc[Capture Screenshot] |A screenshot encoded and written off the frame thread, and the output-directory sandbox refusing a path that escapes it
|{src}/examples/http_fetch/main.roc[HTTP Fetch] |An HTTP GET on a task, re-fetchable mid-flight, with each reply carrying the id of the fetch it belongs to
|{src}/examples/udp_cursor/main.roc[UDP Cursor] |Two instances showing each other's pointer: a receiving task restarted each time it answers, and sends made straight from `update!`
|{src}/examples/sqlite_scores/main.roc[SQLite Scores] |A high-score board that survives a restart: the write and the re-read share one task, so the model is told what the database holds rather than guessing
|===

== Conventions used here

* Keep application state in `Model`; fold `App.Input` into it in pure helpers
  that `update!` calls.
* Load and prepare long-lived resources once in `init!`, then retain them in
  the model instead of recreating them each frame.
* Derive layout and view-only values with pure helpers. Use `frame.size!()`
  for the active surface instead of copying `input.window.size` into the model.
* Call host effects directly from `update!` for work that answers immediately;
  use `Task.spawn!(input, || ...)` for work that waits, and fold its return
  value in when it arrives as a message on a later `input.messages`.
* Give each kind of deferred work its own `Msg` variant. Add an id only when
  multiple instances of the same work may be in flight.
* Keep rules in pure functions so `roc test` can exercise them without calling
  effectful `update!`.
* Treat capture, scripted input, and headless execution as useful app modes,
  not as branches inside ordinary interaction logic.

Exhaustive API probes and invalid-input cases belong in the repository's
{tree}/test[`test/`] directory, where they can be explicit without making an
example harder to understand.

== Permissions in the examples

Each example declares what it reaches beyond its own resources in its startup
config, as <<permissions>> describes: `http_fetch` declares the one origin it
fetches, `udp_cursor` declares loopback networking, and the asset-loading
examples declare their own asset directory, read-only. Nothing is passed on the
command line. Printing, recording, and captures need no declaration, so most
examples declare nothing. Recording examples start capture explicitly in
`init!`.
