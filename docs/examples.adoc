[#examples]
= Example gallery

The repository's `examples/` directory holds complete apps and focused
recipes. This chapter helps you choose which to read. It assumes you have run
an example, as <<run-an-example>> shows.

Each example is a directory with a `main.roc`. Choose the one closest to
what you want to build and copy its directory. For the released examples,
download the examples zip described in <<run-an-example>>; the checked-in
examples on `main` may use APIs that have not been released yet (see
<<development-checkout>>).

Run every command from the directory that contains `examples/`, so the paths
the examples use for their files resolve. To try an example, run it with
`roc`:

[source,sh]
----
roc examples/snake/main.roc
----

To build an executable you can run again, use `roc build`:

[source,sh]
----
roc build examples/snake/main.roc --output=snake
./snake
----

Every example quits when you press Escape unless its header says otherwise.

== Start here

Work through these in order. Each one adds a little to the one before it.

. {src}/examples/hello_world/main.roc[Hello World] (`hello_world`): the
  complete app loop (`init!`, `update!`, and `render!`) with drawing and the
  pointer, and nothing else.
. {src}/examples/move_box/main.roc[Move Box] (`move_box`): a box moved with
  the arrow keys. It introduces moving by speed times elapsed time, and a pure
  function tested with `expect`. <<first-game>> grows the same idea into a
  whole game, one step at a time; Move Box shows the finished result on one
  page, ready to copy.
. {src}/examples/sprite_and_sound/main.roc[Sprite and Sound]
  (`sprite_and_sound`): a picture and a sound loaded from files. It introduces
  a permission, an asset store, and loaded resources.
. {src}/examples/pong/main.roc[Pong] (`pong`): one player against a computer
  paddle. It combines movement, collision, input, scoring, and sounds made in
  code in one approachable file.
. {src}/examples/snake/main.roc[Snake] (`snake`): a grid game split across a
  few modules, with a fixed simulation step and seeded randomness.
. {src}/examples/task_sleep/main.roc[Task Sleep] (`task_sleep`): one task that
  waits, and the message it sends back. Read it before adding files,
  networking, or any other operation that waits.

Then pick a direction:

* *A game:* {src}/examples/breakout/main.roc[Breakout], then
  {src}/examples/top_down/main.roc[Spark Run] or
  {src}/examples/cave_climb/main.roc[Cave Climb].
* *A tool or an app interface:*
  {src}/examples/generated_assets/main.roc[Pixel Workshop],
  {src}/examples/responsive_ui/main.roc[Responsive Settings], or
  {src}/examples/input_inspector/main.roc[Input Inspector].
* *Files, networking, or storage:* the examples under <<examples-waiting>>.
* *A particular drawing technique:* the <<examples-recipes>>.

== Conventions used here

* Each app names its three functions' parameters the same way:
  `init!` takes `io`, `update!` takes `model, input, io` and reads devices
  through `devices = input.devices`, and `render!` takes `model, frame`.
* Keep application state in `Model`; compute the next model from `App.Input`
  in pure helper functions that `update!` calls.
* Load and prepare long-lived resources once in `init!`, then keep them in the
  model instead of recreating them every host cycle.
* Derive layout and view-only values with pure helpers. Use `frame.size!()`
  for the surface being drawn to instead of copying `input.window.size` into
  the model.
* Move by elapsed time, and clamp it: after a pause, one host cycle can report
  a second or more.
* Call host effects directly from `update!` when they return immediately; use
  `+Task.spawn!(input, || ...)+` for anything that waits, and update the model
  with its result when it arrives as a message on a later `input.messages`.
* Give each kind of task its own `Msg` variant. Add an id only when several
  tasks of the same kind may be running at once.
* Keep game logic in pure functions so `roc test` can check them without calling
  effectful `update!`.
* Let `App.default` handle Escape. An app that needs Escape for itself sets
  `with_exit_key(NoExitKey)` and says why, as Input Inspector does.
* Keep capture, scripted input, and headless runs out of ordinary
  interaction: an example never saves, records, or quits by itself during an
  interactive run.

Exhaustive API probes and invalid-input cases belong in the repository's
{tree}/test[`test/`] directory, where they can be explicit without making an
example harder to understand.

== Recording the gallery

The animations in the repository README are recorded by the examples
themselves. Breakout, Pixel Workshop, Responsive Settings, Postcard Studio,
Particles, Spark Run, and Live Plot each take a `--record-demo` argument:

[source,sh]
----
roc examples/breakout/main.roc -- --record-demo
----

The window stays hidden, a scripted demo plays through the app's normal input
path, and the recording is written to `examples/gallery/<directory>.gif`. The
app exits once the file is written. Every one of these apps follows the same
shape: a `demo_recording` value, started in `init!` when the argument is
present, and a pure `demo_finished` that ends the run when `input.capture`
reports the recording `Finished` or `Failed`.

== Permissions in the examples

An example declares, in its startup config, anything it accesses beyond its
own resources, as <<permissions>> describes. Nothing is passed on the command line.

[cols="2,5,3",options="header"]
|===
|Example |Declares |Why
|`sprite_and_sound` |`Directory("examples/sprite_and_sound/assets", ReadOnly)` |Loads its picture and sound from that directory
|`post_process` |`Directory("examples/post_process/assets", ReadOnly)` |Loads its shader from that directory
|`top_down` |`Directory("examples/top_down/assets", ReadOnly)` |Loads its map, textures, music, and sounds
|`cave_climb` |`Directory("examples/cave_climb/assets", ReadOnly)` |Loads its map and textures
|`async_read` |`WorkingDirectory(ReadOnly)` |Reads files beneath the directory it runs from
|`live_plot` |`WorkingDirectory(ReadOnly)` |Lists and reads the whole tree it runs from
|`input_inspector` |`ClipboardRead`, `ClipboardWrite` |Copies and pastes text
|`http_fetch` |`HttpOrigin(url)` for the one URL it fetches |Fetches that URL, and nothing else
|`udp_cursor` |`UdpLoopback` |Sends and receives datagrams on this machine only
|`sqlite_scores` |No permission; names itself with `with_app_id("dev.roc-ray.sqlite-scores")` |Keeps its database in its own private data directory, which needs no declaration
|===

Every other example declares nothing. Printing, drawing, audio, sounds and
textures made in code, a dropped file, and captures written beneath the
output directory all need no declaration.

The recording examples list `PermissionDenied` among the errors `init!` can
return. It comes from `Capture.Writer.start!`, whose result type includes it;
the `io` that `init!` receives always has permission to record, so in these
examples it does not occur.
