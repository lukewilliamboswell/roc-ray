[#files-and-assets]
= Files, assets, and databases

This chapter covers reading and writing files, loading textures, sounds,
fonts, and maps from disk, opening a file the user drops on the window or
names on the command line, and keeping data in SQLite. It assumes <<tasks>>, because everything here that
touches the disk waits, and <<permissions>>, because most directories must be
declared.

== Directory handles, not paths

A handle limits what code can touch. A helper or a task that receives a
handle can use only the files inside that directory, so a bug, or a strange
file name that arrives at run time, cannot lead it anywhere else. It also
makes access easy to follow: to see what a piece of code can read or write,
look at the handles it receives.

An app never names a file by a bare path such as `"saves/slot1.json"` on its
own. It first asks `io.files()` for a _directory handle_, then names files
relative to that handle:

[source,roc]
----
init! = App.init(
    App.default.with_app_id("dev.example.notes"),
    |io| {
        saves = io.files().app_data!()?
        Ok({ saves: saves })
    },
)

update! = |model, input, _io| {
    if input.devices.key_pressed(KeyS) {
        saves = model.saves
        Task.spawn!(input, || Saved(saves.write_text!("slot1.json", encode(model))))
    }
    Ok(model)
}
----

Here `encode` stands for the app's own serializer, and `Saved` is a `Msg`
variant holding the write's result.

A handle is an ordinary value. Keep it in the model, pass it to a helper, or
capture it in a task. Code that has the handle can access the files and
directories inside that directory, and nothing else.

There are two kinds: a `Files.Dir` can read and write, and a `Files.ReadDir`
can only read. A write through a `ReadDir` does not compile.

== Where a handle comes from

Each of these is a method of `io.files()`, such as `io.files().app_data!()`.

[cols="2,1,3",options="header"]
|===
|Method |Returns |Needs
|`app_data!()`, `app_config!()`, `app_cache!()` |`Dir` |No declaration, but the app must name itself with `+App.default.with_app_id(...)+`. These are the app's private directories under the user's home, created on first use.
|`beside_executable!()` |`ReadDir` |Nothing. This is the directory the executable is in, where a packaged app keeps its own files.
|`working_directory!()` |`Dir` |`WorkingDirectory(ReadWrite)` or `FilesAny(ReadWrite)`
|`working_directory_read!()` |`ReadDir` |`WorkingDirectory` or `FilesAny`, in either mode
|`open_dir!(path)` |`Dir` |A `ReadWrite` declaration covering `path`: a `Directory` it lies beneath, `WorkingDirectory` if `path` is relative, or `FilesAny`. The directory is created if it is not there.
|`open_dir_read!(path)` |`ReadDir` |The same, in either mode
|===

An app id is a reverse-DNS style name the app will keep, such as
`"dev.example.pong"`: 1 to 128 ASCII letters, digits, `.`, `-`, or `_`. It
becomes a directory name, so if you change it later, the app can no longer
find its saved data. <<shipping-app-id>> lists where each system keeps these directories.

A path given to `open_dir!` or `open_dir_read!` is matched against the
declarations as written, not looked up on disk; <<permissions>> explains how.
A relative one names a directory beneath the working directory.

Two pure methods narrow a handle without touching the disk:

* `dir.subdir("levels")` returns a handle to a directory beneath `dir`. It
  returns `Try(_, [PathInvalid])`, because the name might not be a plain
  relative path, so write `dir.subdir("levels")?` in `init!` or a task.
* `dir.read_only()` turns a `Dir` into a `ReadDir`.

Pass the narrowest handle a helper needs.

== Reading and writing

Every handle has:

* `read_text!(path)`: a UTF-8 file as a `Str`, up to 64 KiB;
* `read_bytes!(path)`: a file as a `List(U8)`, up to 16 MiB;
* `list!(path)`: the entries of a directory, each a name and a kind (`File`,
  `Dir`, or `Other`);
* `metadata!(path)`: a path's kind, size in bytes, and modification time.

A `Dir` adds `write_text!(path, text)` and `write_bytes!(path, bytes)`.

All of these wait. Call them in `init!`, where they delay startup, or in a
task:

[source,roc]
----
repo = model.repo
Task.spawn!(input, || SmallReadFinished(repo.read_text!("README.md")))
----

Each returns a typed error the app can `match` on. For a read:

* `NotFound`: no file at that path;
* `TooLarge`: a file past the size limit;
* `NotUtf8`: a file that is not valid text (`read_text!` only);
* `PathInvalid` and `PermissionDenied`: see below;
* `ReadFailed`: anything else, including the operating system refusing the
  read;
* `Busy`: the host's 32 file-delivery slots are all held by byte lists the
  app has kept, so nothing was read and the same call can succeed later;
* `Unavailable`: the app was shutting down.

The {api}[API reference] lists every error for every effect.

=== Paths beneath a handle

A path given to a handle is plainly relative: no leading `/`, no drive letter,
no backslash, and no empty, `.`, or `..` component. Symbolic links beneath a
handle are not followed, and a write never replaces one. A path that breaks
either rule returns `PathInvalid`, whether or not it would lead outside the
handle.

`PermissionDenied` means the handle gives no access: it is a `stub` made for
tests.

When the operating system itself refuses, the result depends on the effect. A
write, `metadata!`, or a directory open returns `AccessRefused`. A read
returns `ReadFailed`, because the host cannot tell a refusal apart from other
read failures; call `metadata!` on the path to find out which it was.

[#files-designated]
== Files the user chooses

A file dropped on the window, or a path passed on the command line, needs no
declaration: the user's choice of that file counts as permission. The app turns it into a
`Files.Designated` handle scoped to exactly that file or directory.

A dropped path arrives in `input.dropped`. Accept it in the same `update!`
that received it, then read through the handle on a task:

[source,roc]
----
# For each `drop` in `input.dropped`, inside update!:
match io.files().accept_drop!(drop.path) {
    Ok(item) => Task.spawn!(input, || Opened(item.read_bytes!()))
    Err(PermissionDenied) => {}
}
----

A dropped path kept past that `update!` is only a string; it can no longer be
accepted.

A command-line argument is accepted with `io.files().from_arg!(arg)`. It is
accepted only if it is exactly one of the arguments the app was launched with.

There is no file-picker dialog.

== Asset stores

Textures, sounds, music, fonts, shaders, and maps are loaded from an _asset
store_: a directory opened from a `ReadDir`. The store can access exactly what
that handle can access, so loading an asset can never read outside that
directory. The code that loads assets is the same during development and
after packaging; only the handle changes. Where the handle comes from depends
on how the app runs:

* While you develop, you run the app with `roc` from its source directory.
  Declare the `assets` directory and open it by path, as
  <<drawing-first-sprite>> shows:
+
[source,roc]
----
App.default.with_permission(Directory("assets", ReadOnly))

# In init!:
store = Assets.open!(io.files().open_dir_read!("assets")?, IgnoreManifest)?
----
* Once you package the game, its `assets` directory is next to the
  executable, which needs no declaration:
+
[source,roc]
----
exe_dir = io.files().beside_executable!()?
store = Assets.open!(exe_dir.subdir("assets")?, IgnoreManifest)?
----

`roc main.roc` builds the executable in the compiler's cache, so nothing is
beside it during development. <<shipping>> shows one `init!` that uses the
source directory while you develop and the directory beside the executable
once the game is packaged. The repository's examples run from the repository
root, so they declare their own directory, such as
`Directory("examples/top_down/assets", ReadOnly)`.

Load from a store with:

[cols="2,3",options="header"]
|===
|Loader |Returns
|`Assets.load_texture!(store, path)` |A texture
|`Audio.load_sound!(store, path)` |A sound effect, decoded into memory
|`Audio.load_music!(store, path)` |A music track, streamed
|`Tilemap.load_tmx!(store, path)` |A parsed Tiled map, ready to bind to textures
|`Draw.load_store_font!(store, font)` |A font
|`Draw.Shader.from_store!(store, shader)` |A shader
|===

Opening a store and loading from it wait, so they belong in `init!` or a
task. Load long-lived resources once in `init!` and keep them in the model. To
load something after startup, load it in a task and keep the resource that its
message contains.

A path given to a loader is relative to the store. One that would leave the
store, or that meets a symbolic link, returns `PathInvalid` rather than being
rewritten.

The host keeps a fixed number of each kind of resource: for example, 128
textures and 128 sounds at once. A load past that number returns
`ResourceLimit`. A resource is released when the app drops its last reference
to it, which frees its place for another. <<reference>> lists every limit.

`Assets.open!` takes a manifest policy as its second argument. Pass
`IgnoreManifest` to open a directory of loose files, which is what almost
every app wants.

=== Details: asset manifests

`RequireManifest(expectation)` fails the open unless a `roc-assets.manifest`
file in the store declares the expected asset set, schema version, content
version, and, optionally, a SHA-256 content hash. The open compares these
against what the manifest declares; it does not read or hash the asset files,
so opening a store stays fast however many assets it holds. It confirms the
store is the release you packaged, not that its files are intact.

The repository's `scripts/asset_manifest.py` generates and verifies a
deterministic manifest for a directory of loose assets, which gives packaging
and CI a stable content revision.

== SQLite databases

RocRay includes SQLite. A database file is opened through a directory handle,
usually the handle for the app's own data directory:

[source,roc]
----
data = io.files().app_data!()?
db = io.sqlite().open!(data, "scores.db")?
db.exec_script!(schema)?
rows = db.query!(top_ten, [])?
----

* `io.sqlite().open!(dir, name)` opens or creates a database beneath a `Dir`.
* `io.sqlite().open_read!(read_dir, name)` opens one read-only beneath a
  `ReadDir`.
* `io.sqlite().open_memory!()` creates a private in-memory database, which
  needs no handle.

Every database effect waits, so it runs in `init!` or a task. Use
`db.query!(sql, bindings)` and `db.execute!(sql, bindings)` for one-off SQL,
and keep a prepared statement from `db.prepare!(sql)` when running the same SQL
repeatedly.
Transactions use explicit `BEGIN`, `COMMIT`, and `ROLLBACK`. Rows are decoded
with pure, typed accessors such as `row.str("name")`.

`ATTACH` is disabled on every connection, so a database cannot open a second
file outside its handle. At most eight connections and sixty-four statements
may be open. A query whose result exceeds one million cells, or the configured
byte limit (16 MiB by default), is refused rather than truncated.
Databases and statements close automatically when their last reference goes
away; `Db.close!` closes one early.

{src}/examples/sqlite_scores/main.roc[SQLite Scores] keeps a high-score table
that survives a restart.
