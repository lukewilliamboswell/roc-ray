[#overview]
= What RocRay is

RocRay lets you write 2D games, visualizations, creative tools, and other
interactive programs in https://www.roc-lang.org/[Roc]. It draws with
https://www.raylib.com/[raylib], a popular C library for games, and runs on
macOS (Intel and Apple silicon), Linux x86-64, and Windows x86-64.

It suits programs that draw a fresh picture many times a second: arcade and
puzzle games, simulations, live plots, generative art, and small editors.

RocRay is 2D. It draws shapes, images, and text, and it has 2D cameras,
shaders, and offscreen drawing. It does not draw 3D models or provide 3D
cameras or lighting.

RocRay is a focused platform, not a game engine. Your app keeps its own state
and rules. RocRay provides drawing, sound, keyboard, mouse and gamepad input,
the window, screen recording, files, and networking. It does not give you a
scene graph, an entity system, or an editor; build those in Roc, or use a
package, if your app needs them.

If you already know raylib, <<coming-from-raylib>> shows how its functions and
habits map onto RocRay.

== What you write

A RocRay app is three functions:

* `init!` runs once, at startup. It chooses the window's settings, loads what
  the app needs, and creates the starting state, which RocRay calls the
  _model_.
* `update!` receives the model and what just happened -- keys pressed, the
  mouse moving, work that finished -- and returns the next model.
* `render!` draws the model.

The _host_, the native program that runs your app, calls them in a loop. One
pass around that loop is a _host cycle_: the host gathers what happened, calls
`update!` once, and then calls `render!` to draw the result. Each picture
`render!` draws is a _frame_. Normally every host cycle draws one frame, so a
game running at 60 frames a second also runs 60 host cycles a second. The two
differ only when the host skips drawing, for example while the window is
minimized.

Reading a file or waiting for a network reply can take longer than one host
cycle. That work runs as a _task_, so the app keeps updating and drawing while
it waits. When the task finishes, its result arrives in a later `update!`.

<<app-model>> explains these pieces in full. You do not need them to run your
first example. <<glossary>> defines every term the manual uses.

== What an app can reach

Every app can draw, read input, play sound, print to its terminal, and record
itself. Reaching further -- a network service, a directory, another program,
an environment variable, the clipboard -- is declared in the app's startup
settings, so you can see what an app can reach by reading its source.
<<permissions>> explains how.

== What it looks like

Three short examples are the best place to start:
{src}/examples/hello_world/main.roc[Hello World], a circle that follows the
mouse; {src}/examples/pong/main.roc[Pong], a complete game in one file; and
{src}/examples/snake/main.roc[Snake], a grid game you can restart.

These larger apps are also in the repository's `examples/` directory, roughly
from simplest to most involved. Each links to its complete Roc source.

== Stability

RocRay follows Roc's newest compiler closely, and its API may still change as
the language evolves. Each release names the exact Roc compiler it was built
and tested with. Bug reports, documentation improvements, and focused new
capabilities are welcome; see <<contributing>>.
