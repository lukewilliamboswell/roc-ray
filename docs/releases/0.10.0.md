# RocRay 0.10.0

0.10.0 is the largest change to RocRay so far. The application model has been rebuilt: state changes and drawing are now separate callbacks, slow work runs as tasks without stalling the frame, and the platform gains files, HTTP, UDP, SQLite, subprocesses, screen capture and more. Every 0.9 app needs to be migrated. The [upgrade guide](#upgrading-from-09) at the end covers each step.

The reasoning behind these changes is written down in [`design.md`](https://github.com/lukewilliamboswell/roc-ray/blob/0.10.0/design.md). These notes summarise it.

## One callback became two

In 0.9, an app had an `init!` and a single `render!`. `render!` read the keyboard from `Host`, advanced the game, played sounds, drew the frame and returned the next model, all in one place:

```roc
# 0.9
render! : Model, Host, Draw.Frame => Try(Model, [Exit(I64), ..])
render! = |model, host, frame| {
    if host.key_pressed(KeyEscape) {
        host.exit!(0)
    }
    next = step(model, host.frame_time, host.key_down(KeyW))
    frame.clear!(Color.black)
    draw_field!(frame, next)
    Ok(next)
}
```

This was easy to start with, but it caused problems as apps grew. Game rules and drawing were mixed together, so the rules were hard to test without a window. Any effect could be called while a frame was being drawn. A file read in the middle of `render!` froze the animation until the disk answered.

In 0.10.0 each callback has one job:

```roc
# 0.10
program = { init!, update!, render! }

update! : Model, App.Input(Msg), App.Io => Try(Model, [Exit(I64)])
update! = |model, input, _io| {
    if input.devices.key_pressed(KeyEscape) {
        Err(Exit(0))
    } else {
        Ok(step(model, input.time.elapsed_seconds, input.devices.key_down(KeyW)))
    }
}

render! : Model, Draw.Frame => Try({}, [Exit(I64)])
render! = |model, frame| {
    frame.clear!(Color.black)
    draw_field!(frame, model)
    Ok({})
}
```

- **`update!` is the only place the model changes.** Once per host cycle it receives an `App.Input`, which holds the devices snapshot (keys, mouse, gamepads), timing, window state, dropped files and the messages from finished tasks. It can call host effects directly, such as playing a sound or resizing the window. Returning `Err(Exit(code))` ends the app.
- **`render!` only draws.** It receives the updated model and a `Draw.Frame`, and returns `{}`, not a model. Drawing is only allowed here, and state-changing effects are refused here, so a frame always shows the model that `update!` just produced.
- **Rules can be tested without a window.** Input and host resources have pure constructors, so the decisions inside `update!` can be checked with `expect`:

  ```roc
  expect read_controls(Devices.none.with_key_down(KeyW)).move == -1
  expect read_controls(Devices.none.with_key_pressed(KeyEscape)).quit_pressed
  ```

  `App.Input.for_tests` builds a whole input the same way, and every host resource (textures, fonts, sounds and so on) has a `stub`, so a model that holds assets can be built inside a test.

The examples were rewritten to show this structure. [Pong](https://github.com/lukewilliamboswell/roc-ray/blob/0.10.0/examples/pong/main.roc) is a good place to start: it turns keys into semantic controls, advances a pure `World`, and plays sounds from the events that step reports.

## Work that waits runs on a task

Reading a file, fetching a URL or querying a database can take longer than a frame. In 0.10.0 that work runs on a **task**. A task is an effectful closure started with `Task.spawn!`. When it waits, only the task pauses; the app keeps updating and drawing. When the closure returns, its value arrives as a message on a later `input.messages`:

```roc
Msg : [Loaded(Try(Str, Files.ReadTextError))]

update! = |model, input, io| {
    if input.devices.key_pressed(KeyEnter) {
        files = io.files()
        Task.spawn!(input, || Loaded(files.read_text!("level.json")))
    }
    Ok(List.fold(input.messages, model, apply_message))
}
```

Inside a task, a waiting effect simply returns its answer. A job with several steps, such as loading a file, parsing it, then fetching a URL it names, is ordinary top-to-bottom code with `?`. It does not need to be split across message variants. The [SQLite Scores](https://github.com/lukewilliamboswell/roc-ray/blob/0.10.0/examples/sqlite_scores/main.roc) example writes a score and reads the board back in one task, so the model always gets what the database actually holds.

Some design decisions to be aware of:

- **Tasks run on the frame thread.** Each task has its own stack, but only one piece of Roc code runs at a time. Roc values carry reference counts, so sharing them between threads is unsafe. Host worker threads do the actual I/O and only handle bytes the host owns. Your code never needs a lock and never sees a half-updated model. The trade-off is that a task doing heavy computation without waiting still delays the frame, just as it would in `update!`. Tasks let slow I/O overlap with frames; they do not add parallel computation.
- **Each task delivers exactly one message.** Messages arrive in the order tasks finish. A finished task's message is never dropped while the app is running.
- **Spawning never fails.** Up to 32 tasks run at once. Extra spawns are queued and started in order as slots free up. When the app exits, running tasks are cancelled and queued ones are dropped.
- **`Task.spawn!` takes the current `input`** as its first argument. It is not read. It is there so the compiler can check that the closure returns your app's `Msg` type.
- **Waiting effects are checked at runtime.** An effect that can wait is refused in `update!` and `render!`. Calling one there stops the app with a message naming the effect, the callback it was called from, and where it belongs. The compiler cannot catch this, so the platform checks it at runtime instead. In exchange, effects are ordinary function calls rather than values you build and hand to the host. Every effect's documentation lists where it is allowed.

If you tried the release candidates, you may remember a different design. We first tried Elm's approach: a pure `update` that returned command values for the host to perform. It worked, but any job with several steps turned into a state machine spread across messages. After [@obust](https://github.com/obust) reviewed that API, we replaced it with the effectful `update!` and tasks described above.

## External services are opt-in

External services are now reached through `App.Io`. `init!` and every `update!` receive it, and you select a service from it:

```roc
files = io.files()
response = io.http().send!(request)?   # in init! or a task
```

The available services are `files`, `http`, `udp`, `sqlite`, `commands`, `stdout`, `stderr`, `clipboard`, `env`, `capture`, and the asset loaders `assets`, `audio` and `tilemaps`. A service value can be passed to a helper or captured by a task, so each piece of code only receives the access it needs.

**All external services are denied by default.** Until the app is launched with `--host-caps-allow-all`, they return `PermissionDenied` without doing anything:

```sh
roc examples/http_fetch/main.roc -- --host-caps-allow-all
./my-game --host-caps-allow-all
```

This covers anything that reaches outside the app: files (including asset files and writes to the working directory), network, subprocesses, SQLite, environment variables, the clipboard, stdout/stderr, and capture output. Drawing, input, window control, audio playback, generated resources, clocks, timers and entropy are always available.

The goal is that an app you download cannot read your files or reach the network unless you start it that way, and that access is described by types that narrower permissions can build on later. **This is not an OS sandbox.** Once granted, file access is not restricted to a directory, HTTP is not restricted to an origin, and subprocesses can run any program.

**If your app loads textures, sounds, fonts or maps from disk, it needs `--host-caps-allow-all`.** Loading an asset reads the filesystem.

## New capabilities

- **Files:** `read_text!`, `read_bytes!`, `list!`, `metadata!`, `write_text!` and `write_bytes!`. Large reads are handed to Roc without an extra copy.
- **HTTP client:** `send!`, `send_with!`, `send_json!`, `get!` and `get_utf8!`, with timeouts and a response size cap. See [`http_fetch`](https://github.com/lukewilliamboswell/roc-ray/blob/0.10.0/examples/http_fetch/main.roc).
- **UDP:** `bind!`, `send!` (queued, returns immediately) and `receive!`, which waits inside a task and returns every datagram that arrived, in a batch. See [`udp_cursor`](https://github.com/lukewilliamboswell/roc-ray/blob/0.10.0/examples/udp_cursor/main.roc).
- **SQLite:** a bundled SQLite 3.50.4 with typed database and statement handles, and pure row decoders.
- **Subprocesses:** `Cmd` requires a timeout and output limits. A nonzero exit code is returned as data, and child processes are killed when the app exits.
- **Standard output and error:** `io.stdout().line!(...)` can be called from `update!`. Writes go into a bounded host buffer and are flushed on another thread, so printing never stalls a frame. A full buffer is reported as a result, not a silent drop.
- **Time and randomness:** `Time.now!` returns a UTC `Time.Timestamp`. `io.entropy!()` returns real OS entropy, which can seed a pure `Random` generator stored in the model. After seeding, an entire run can be replayed from that one number.
- **Screenshots and recordings:** apps can capture themselves as PNG screenshots, PNG sequences, animated GIFs or VP8/WebM video. Fixed-step timing produces byte-identical recordings across runs. A hidden window renders on the GPU with nothing shown on screen, so an app can run as a batch job. Scripted mouse and keyboard input (`Mouse.set_source!`, `Keys.set_source!`, `Keys.set_text!`) goes through the same path as real input, so recorded UI demos use the app's normal code. `Capture.screenshot_texture!` exports an off-screen render target at any size, and `Capture.pixel_at!` and `read_region!` read pixels back.
- **Window:** minimum size, a configurable exit key, clipboard access, display scale, monitor list, and drag-and-drop (`input.dropped`). Window sizing and placement use `suggest_*` names, because the window manager may ignore the request.
- **Text and fonts:** `Text.Font` includes its metrics, so `font.measure(...)` is a pure function that layout code and packages can call. `Text.from(str, font).size(n).prepare!()` lays out text once for repeated drawing. `App.Config.with_default_font` loads one font for the whole app at startup.
- **Asset stores:** `io.assets().open!(Assets.working_directory("assets"))` resolves paths relative to a directory and refuses paths that escape it. An optional manifest can check the store's contents against expected hashes.
- **Batched drawing:** `frame.texture_instances!` draws thousands of sprites in one call. See [`particles`](https://github.com/lukewilliamboswell/roc-ray/blob/0.10.0/examples/particles/main.roc).

## Input events are no longer lost between frames

raylib stores the *current state* of keys and buttons, not a history of changes. A key tapped and released between two frames, a quick double click, or two scroll notches could collapse into one reading or vanish, depending on the frame rate.

The host now records key, mouse button, scroll and character events as they arrive from the window system and delivers them on the next input. `input.devices.events` lists every event in order, and each click records the pointer position where it happened. The list holds up to 256 events per cycle. If more arrive, `events_overflow` is set, so events are never lost silently. The `key_pressed` and `key_released` checks are built from the same records, so a tap between frames now shows as both pressed and released. Typed text is kept in the same way.

Gamepad buttons are still sampled once per frame because raylib provides no event callback for them. Their documentation says so.

## Performance

- **The model is no longer copied every frame.** With older compilers, changing a large list in the model copied the whole list on every frame. With the current compiler it is updated in place. A million-element list now costs 88 bytes per frame instead of 4 MB, so large collections in the model are no longer a performance problem.
- **RocRay Observatory.** Launch any app with `--host-stats-record` to record host cycles, callbacks, tasks, effects, allocations and draw activity to a SQLite `.rrstats` file. The `Trace` module lets you add your own marks and timed zones. The [Observatory guide](https://github.com/lukewilliamboswell/roc-ray/blob/0.10.0/docs/observatory.md) includes ready-made queries. We used it to speed up the examples: Cave Climb, for example, went from 69 draw calls to 31 per frame.

## One package instead of two

During the release candidates, RocRay's types were published in a separate `roc-ray-types` package so that other packages could use them. That meant two releases that had to stay in sync, split documentation, and packaging bugs in the compiler. In 0.10.0 the platform is the only source of its API: types, pure helpers and effects are all versioned, documented and released together. Reusable packages should define their own data types and let the app convert platform values into them.

## Upgrading from 0.9

**Update the header.** Use the platform URL and compiler listed at the end of these notes, and add `update!` to `program`:

```roc
app [Model, program] { rr: platform "<bundle URL below>" }

program = { init!, update!, render! }
```

**Split `render!`.** Move everything that reads input, advances state or calls a non-drawing effect into `update!`. Change `render!` to `render! : Model, Draw.Frame => Try({}, [Exit(I64)])` and return `Ok({})`. The rest of the migration is mostly renames:

| 0.9 | 0.10 |
| --- | --- |
| `init!`'s `run!` receives `Host` | `App.init(config, \|io\| ...)`, and `run!` receives `App.Io` |
| `host.key_pressed(k)`, `host.key_down(k)` | `input.devices.key_pressed(k)`, `input.devices.key_down(k)` |
| `host.mouse`, `host.gamepads` | `input.devices.mouse`, `input.devices.gamepads` |
| `host.frame_time` | `input.time.elapsed_seconds` |
| `host.exit!(code)` | return `Err(Exit(code))` from `update!` |
| `host.random_i32!(lo, hi)` | a `Random.State` in the model, seeded once from `io.entropy!()` |
| `host.read_file!(path)` | `io.files().read_text!(path)` in `init!` or a task |
| `host.read_env!(name)` | `io.env().read!(name)` |
| `host.set_screen_size!(size)` | `Window.suggest_size!(size)` |
| `Assets.load_texture!(path)` | `store = io.assets().open!(...)`, then `Assets.load_texture!(store, path)` |
| `Audio.load_sound!(path)` | `io.audio().load_sound!(path)` |
| `Color.Color` | `Color.Rgba` |
| `frame.text!({ ..., font, align })` | `frame.text_at!({ pos, text, size, color })`, or `Text.from(str, font).size(n).draw!(frame, { pos, color, align: (Top, Center) })` |

**Load files in `init!` or a task.** Loading textures, sounds, music, shaders and TMX maps from disk now waits, so it is only allowed in `init!` (which holds startup until it finishes) or in a task. Creating resources from bytes you already have (`*_from_bytes!`, `gen_*`, generated textures) still works in `update!`.

**Launch with `--host-caps-allow-all`** if your app reads assets from disk, uses the network, or writes files or captures. Without it, those calls return `PermissionDenied`. Your error handling may need to cover that new case.

**Remove `..` from return-position tag unions.** The supported compiler treats tag unions in return position as open automatically, and reports an explicit `..` there as a redundant-open-union warning, which fails `roc check`. Write `Try(Model, [Exit(I64)])` instead of `Try(Model, [Exit(I64), ..])`.

**If you tried a release candidate** and depended on `roc-ray-types`, remove that dependency and import the same modules from the platform (`rr.Devices`, `rr.Math`, `rr.Text` and so on).

The [examples](https://github.com/lukewilliamboswell/roc-ray/tree/0.10.0/examples) show the finished shape. Every 0.9 example still exists under the same name, now as `examples/<name>/main.roc`, so each one makes a useful before-and-after comparison.

## Fixes

- **HiDPI macOS:** everything drawn inside a 2D camera appeared at half size in the top-left quarter of the window ([#166](https://github.com/lukewilliamboswell/roc-ray/pull/166)).
- **Texture uploads:** `update_texture!` and `update_texture_region!` reversed the colour channels, so blue appeared grey and yellow appeared pink ([#168](https://github.com/lukewilliamboswell/roc-ray/pull/168)).
- **Input:** presses, releases, clicks and scroll notches between two frames could be lost ([#180](https://github.com/lukewilliamboswell/roc-ray/pull/180)).
- **Headless runs:** random numbers were identical on every run. `io.entropy!()` now returns real OS entropy in every mode.
- **Errors:** host effects now return typed error unions instead of numeric codes, so each failure is a tag your app can `match` on.

## Documentation, examples and tooling

- The API docs are one site for the whole platform, and every effect lists the callbacks it is allowed in.
- Each release includes an examples zip whose headers already point at that release's bundles.
- The examples were redesigned. Larger games such as Top Down and Cave Climb are split into focused modules with pure, testable rules.
- CI now runs every example against the real raylib backend in a hidden window on Linux and Windows, in addition to the headless runs on every OS.
- Native dependencies (raylib, libvpx, SQLite and the macOS linker interfaces) are built by a separate workflow that publishes attested archives. Builds install the archives pinned by digest in `link-inputs.lock.json`, and releases verify their attestations, instead of compiling those dependencies.
